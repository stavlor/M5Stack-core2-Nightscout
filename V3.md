# Nightscout API v3 transport

V3 is now the default in include/ns_settings.h (USE_V3=true). Existing URL,
read-only subject token and Wi-Fi values in config.h are used unchanged. The
server must provide API v3 and the standard v2 authorization-request endpoint.

The firmware exchanges the subject token over validated HTTPS for a temporary
JWT, sends Authorization: Bearer on data requests, caches the JWT only in RAM,
and renews 60 seconds before expiration. One 401-triggered renewal/retry is
allowed per data request. Further authentication failures enter a 30-second
cooldown to avoid repeatedly authenticating for each of the three endpoints.
403 permission failures and missing v3 endpoints do not silently downgrade.

The authorization endpoint is GET /api/v2/authorization/request/{subject-token}.
Nightscout's standard protocol puts that credential in the TLS-protected path.
The firmware never logs it or the JWT and disables underlying HTTP debug logs.
Reverse proxies/server access logs should redact this route or omit its path.
JWTs are never written to Preferences, files or diagnostic output. Response
sizes and expiry values are validated; missing/expired/malformed tokens fail
closed. TLS roots, hostname checks, valid-clock gating and redirect rejection
remain enabled.

Read-only v3 search requests:

- entries: type$eq=sgv, date range, sort$desc=date, limit=288, fields for date,
  SGV, trend and validity. Only the configured graph window is requested.
- devicestatus: sort$desc=date, limit=2, selected top-level date/device/openaps/
  pump/validity fields. Optional AAPS_DEVICE adds exact device$eq filtering.
  Set this when multiple uploaders could crowd AAPS out of the latest two
  records. Full openaps and pump objects preserve uploader-specific nested
  fields and are still bounded by the decoded-body limit/client JSON filter.
- treatments: canonical date range, sort$desc=date, limit=200, fields for public
  identifier, event timestamps, carbs, insulin, SMB classification, validity and
  pump identity. The newest 128 qualifying records are retained as before.

V3 status/result envelopes are validated before existing model parsers run.
Malformed/non-success envelopes retain the last good snapshot, which continues
aging. Valid empty results clear it. Canonical numeric date is supported for
status uploads, identifier for treatment identity, and deleted/invalid records
are ignored. Loop/pump/IOB/COB freshness still uses their underlying timestamps;
server modification timestamps never make old clinical data fresh. Alerts use
actual current SGV only. UI, touch controls, graphs and alert settings are unchanged.

The firmware continues bounded full-window polling, not incremental HISTORY
synchronization, so server edits/deletions are reflected on the next successful
snapshot without maintaining tombstone caches. Legacy records missing a usable
canonical date will not match a v3 date search; the parser's date-string fallback
is for returned records rather than an unbounded recovery query. Use the explicit
v1 setting if an older server/uploader cannot provide the v3 schema.

To select the legacy fallback, set USE_V3=false in include/ns_settings.h and
rebuild. This uses the previous v1 queries and api-secret subject-token header.
There is no automatic fallback after an authentication or API error. Token roles
need read on entries, devicestatus and treatments; no write scope is required.

## Approved live server verification

With explicit user approval, the saved read-only subject token was exchanged for
a JWT on the configured Nightscout server. The firmware CA bundle and hostname
validation succeeded. The entries request returned HTTP 200 with 36 records
(2,431 bytes); device status returned HTTP 200 with two records (7,142 bytes)
and a matching OpenAPS snapshot; treatments returned HTTP 200 with 28 records
(6,852 bytes). All three had valid v3 status/result envelopes. No credentials,
URLs or clinical values were displayed or saved. Counts describe this one check.

The first generic Python user-agent was rejected with HTTP 403. Repeating with
the ESP32HTTPClient user-agent succeeded. The firmware now explicitly sets that
user-agent on auth and data requests, matching the successful probe. This does
not disable any TLS checks. Live server compatibility is verified; ESP32 build,
on-device parsing/display and long-running JWT renewal are still pending the
local pre-flash suite and device checks.
