# Nightscout transport: v3 default and explicit v1 fallback

`include/ns_settings.h` selects `USE_V3=true` by default. The existing HTTPS URL,
read-only subject token and Wi-Fi settings in config.h are used. The server must
provide API v3 and the standard v2 authorization-request endpoint.

## JWT authentication

1. GET `/api/v2/authorization/request/{subject-token}` over validated HTTPS.
2. Validate the returned token shape, size and expiration; cache the JWT only in RAM.
3. Send `Authorization: Bearer <JWT>` on v3 collection requests.
4. Renew within 60 seconds of expiration. A data-request 401 allows one renewal
   and one retry. Repeated authentication failure enters a 30-second cooldown.

Auth responses are capped at 8 KiB, token length at 4,096 characters, JSON capacity
at 6 KiB and nesting at eight. Expiration must be an integer later than now+30
seconds and before 2100. JWTs are opaque credentials; the client trusts the
TLS-authenticated server response, not an independently verified JWT signature.

The standard authorization endpoint necessarily places the subject token in its
TLS-protected URL path. The firmware does not log that path, token, JWT or response
body and uses `CORE_DEBUG_LEVEL=0`. Server/proxy access logs should redact this
route or omit its path. JWTs are not saved in Preferences or on disk. TLS chain,
hostname, time and redirect checks remain enabled. Both authentication and data
requests explicitly use `ESP32HTTPClient` as user-agent.

## Bounded collection requests

All are read-only GET searches; parameters use the v3 `$` operator syntax.

| Collection | Selection |
| --- | --- |
| `/api/v3/entries` | `type$eq=sgv`, graph-window `date$gte`, upper `date$lte` at now+120 seconds, `sort$desc=date`, `limit=288` |
| `/api/v3/devicestatus` | `sort$desc=date`, `limit=2`, optional exact `device$eq` |
| `/api/v3/treatments` | Graph-window `date$gte`, `date$lte` at request time, `sort$desc=date`, `limit=200` |

Entries request date, SGV, direction and validity fields. Device status requests
date/created_at, device, openaps, pump and validity fields. It retains complete
openaps/pump objects for uploader compatibility; the client filter then keeps
required nested fields and four supported predBGs curves. Treatments request
identifier, event dates, carbs/insulin, SMB/type/eventType, validity and pump
identity. Data bodies remain capped at 192 KiB and parsed into a 64 KiB document.

Set `AAPS_DEVICE` when multiple uploaders could crowd AAPS out of the two newest
status records. Without it, the client chooses a matching OpenAPS record from
that bounded response; it does not search the whole collection. V3 does not use
the v1-only OpenAPS-exists query.

## Response and date handling

V3 must return numeric `status: 200` and an array `result`. Invalid/non-success
wrappers retain the last good data while it ages. Valid empty arrays clear the
corresponding snapshot. Canonical numeric `date` is supported for device-status
uploads; public `identifier` is preferred for treatment identity. Invalid/deleted
documents are ignored. Underlying calculation/pump timestamps still gate metrics
and forecasts: `srvModified`, upload time or JWT renewal cannot revive old values.

Polling replaces a bounded full-window snapshot; it does not use incremental
HISTORY synchronization or persistent tombstone caches. Server edits/deletions
are reflected on the next successful response within the queried limits. Legacy
records without a usable canonical date will not match a v3 date search; parsing
fallback date strings does not make the query itself unbounded.

UI, overlays, alert logic and mute settings use the existing data models and are
independent of the selected transport.

## Legacy fallback

Set `USE_V3=false` in `include/ns_settings.h`, rebuild and flash. This explicitly
selects the previous v1 entries/device-status/treatments queries and subject-token
`api-secret` header. Bare arrays are accepted only on that path. There is no
automatic downgrade on 401/403, missing v3 endpoints or malformed responses.
Both modes require read rights for entries, devicestatus and treatments; neither
requires write scope.

## Verification and sources

The approved live probe successfully exchanged the saved subject token for a
JWT and read all three v3 collections with the bundled CA and hostname checks.
A generic Python user-agent first received 403; the ESP32 user-agent then succeeded.
This establishes server/protocol compatibility, not completion of on-device
endurance or JWT-expiry testing. Current host-suite/build evidence is in
[VERIFICATION.md](VERIFICATION.md).
